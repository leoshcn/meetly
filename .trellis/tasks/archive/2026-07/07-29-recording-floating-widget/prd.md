# PRD: 录音悬浮窗与关窗拦截

## Goal

消除「会议结束了却忘记停止录音」这个痛点。做法是在录音期间提供一个常驻桌面的悬浮窗，把录音状态和已录时长持续暴露在 Meetly 主窗口之外；并在录音进行中关闭主窗口时拦截，避免录音在用户无感知的情况下被丢弃。

用户价值：会议结束、关掉会议软件之后，屏幕上仍然留着一个跳动的计时药丸，这个反差本身就是提醒。同时录音状态不再因为主窗口被遮挡、被导航走或被关闭而消失。

## Background / Confirmed facts

以下均经代码核实。

**录音是纯手动的。** `record_start` / `record_stop` / `record_status` 是唯一入口（`src-tauri/src/commands/recording.rs:16-40`，注册于 `src-tauri/src/lib.rs:71-74`）。没有静音检测、VAD、时长上限、空闲检测、会议软件进程检测、日历集成，也没有睡眠/锁屏事件处理。状态机只有 `"idle"` / `"recording"` 两个字符串态（`src-tauri/src/services/recording_service.rs:314-332`），没有暂停态。

**`record_status` 已经提供了悬浮窗所需的全部数据。** 返回 `state` / `started_at` / `mic_level` / `system_level`（`src-tauri/src/services/recording_service.rs:47-56`）。`started_at` 是 RFC3339 本地时间（`recording_service.rs:701`），可直接被前端解析用于计算已录时长。`mic_level` / `system_level` 是平滑后的 `[0,1]` RMS，现有波形图已按 40ms 轮询它们（`src/features/meeting-recording/RecordingWaveform.tsx:56-67`）。悬浮窗不需要任何新的音频信号。

**当前只有一个窗口，且没有任何系统级可见性通道。** `tauri.conf.json:13-19` 只声明了 `main`；`capabilities/default.json:5` 是 `"windows": ["main"]`。项目没有托盘、没有系统通知插件、没有全局快捷键、没有置顶窗口。

**已存在缺陷：录音期间导航离开会丢失录音 UI 状态。** 录音状态存在 `MeetingRecordingPanel` 的局部 state（`src/features/meeting-recording/MeetingRecording.tsx:46`），而该组件会被卸载——`AppShellChrome` 是 `screen === "settings" ? <SettingsPage/> : <HomePage/>`（`src/app/AppShell.tsx:95-106`），且 `HomePage` 仅在 `!showWorkspace` 时渲染该面板（`src/pages/home/HomePage.tsx:197-211`）。因此录音中点开设置、或从侧边栏选中另一场会议，界面会退回「开始录音」而后端仍在录，再次点击会撞 `RECORD_BUSY`（`src-tauri/src/services/recording_service.rs:281-282`）。计时也是基于挂载时的 `Date.now()`（`MeetingRecording.tsx:100`），重新挂载会归零。

这条缺陷必须在本任务内修复：悬浮窗会诚实显示「正在录音 12:34」，若主窗口同时显示「开始录音」，两个窗口会自相矛盾。

**停录后的流水线绑在组件回调上。** `endRecording()` 依次执行 `record_stop` → `meetings_create_from_file` / `meetings_attach_source` → `jobs_start_transcription`，结果通过 `onMeetingCreated` 回调交给 `HomePage` 的 state（`MeetingRecording.tsx:136-149`）。这决定了悬浮窗不承担停止动作（见 Key decisions）。

**录音中强退会留下孤儿文件。** 音频以 `.wav.partial` 增量写盘（`recording_service.rs:493-500`、`166-176`），会议行只在停录后才写入数据库。`lib.rs` 没有 `on_window_event`，前端也没有 `beforeunload`，所以录音中关窗会留下一个未 finalize 的 `.wav.partial`，启动时无人扫描。本任务修复「关窗」这一半，不做孤儿文件恢复。

## Key decisions

| 决策 | 结论 | 理由 |
|---|---|---|
| 提醒机制 | 不做静音检测 | 静音检测是在猜「会议是否结束」，误判要么误停要么漏报。悬浮窗不做猜测，直接消除「状态不可见」这个根因，零误判。 |
| 显著性 | 安静的纯展示，不随时长升级 | 用户选定。存在感即状态：它在 = 在录，消失 = 已停。 |
| 可隐藏性 | 不可关闭，但可折叠成极小圆点 | 折叠态解决屏幕共享时的尴尬，同时「在录音」这个信号永不消失。 |
| 悬浮窗是否能停止录音 | 不能。只提供「打开 Meetly」把主窗口唤到前台 | 停录后的流水线依赖 `HomePage` 的回调宿主；给悬浮窗停止按钮就必须把录音会话所有权重构到 `AppShell` 层。与「纯展示」定位一致，且没有误点停录的风险。 |
| 全局快捷键停止 | 排除 | 快捷键要「用户记得按」才有用，而本痛点的前提正是用户不记得。属于效率功能，不是本痛点的解法。 |
| 开始录音时主窗口行为 | 隐藏主窗口并显示系统托盘（录音期间）；托盘/悬浮窗可恢复 | 用户选定。托盘仅在录音期间可见，空闲时不常驻托盘，避免改变日常退出路径。 |

## Requirements

### R1 悬浮窗生命周期
- R1.1 录音开始时悬浮窗出现；录音停止时消失。它的存在与否就是录音状态，不额外显示状态文案。
- R1.2 悬浮窗无关闭按钮，且不响应关闭请求（含 Alt+F4）。
- R1.3 悬浮窗不出现在任务栏、不出现在 Alt+Tab 列表、无窗口装饰。
- R1.4 主窗口最小化或被遮挡时，悬浮窗仍然可见。

### R2 展开态内容
- R2.1 横向药丸形态，含：呼吸红点、等宽数字计时、麦克风与系统两条电平条、「打开 Meetly」入口、「折叠」入口。
- R2.2 电平条数据来自 `record_status` 的 `mic_level` / `system_level`，不引入新的音频采集或信号处理。
- R2.3 计时不足 1 小时显示 `MM:SS`，达到 1 小时后显示 `H:MM:SS`；数字等宽，宽度变化时不产生抖动。

### R3 折叠态
- R3.1 折叠态只显示呼吸红点，不显示时长。
- R3.2 展开态与折叠态之间可双向切换，切换偏好在同一次录音内保持。
- R3.3 折叠态窗口尺寸收紧到圆点大小，不残留透明命中区域。

### R4 计时正确性
- R4.1 已录时长由 `record_status.started_at` 推导，不由前端挂载时刻推导。
- R4.2 主窗口内导航（进设置、切换会议）、悬浮窗折叠/展开，均不导致计时归零或漂移。

### R5 位置与多显示器
- R5.1 悬浮窗可拖动，默认位置为主显示器顶部居中偏下。
- R5.2 位置在应用重启后保持。
- R5.3 显示前校验保存的坐标是否与任一已连接显示器的可见区域相交；不相交则回落到默认位置。
- R5.4 设置中提供「重置悬浮窗位置」。

### R6 唤起主窗口
- R6.1 点击「打开 Meetly」或托盘图标/「打开 Meetly」菜单项，应显示并聚焦主窗口（取消最小化）。录音进行中托盘保持可见。
- R6.2 主窗口被唤起后应处于录音界面，而不是设置页或其他会议的工作区。

### R6b 录音托盘
- R6b.1 开始录音成功后：主窗口隐藏（离开任务栏），系统托盘出现 Meetly 图标（tooltip 含「正在录音」）。
- R6b.2 停止并转写（或关窗拦截停止并保存）后：托盘隐藏；主窗口显示（以便继续转写/查看保存结果）。
- R6b.3 托盘左键点击与「打开 Meetly」菜单：显示并聚焦主窗口，并发出 `recording:focus-request`。
- R6b.4 托盘「退出」：若正在录音，先显示主窗口再触发与关窗相同的三选一询问；若未录音，直接退出进程。

### R7 主窗口录音状态一致性（修复既有缺陷）
- R7.1 `MeetingRecordingPanel` 挂载时依据 `record_status` 恢复录音 UI，包括正确的已录时长。
- R7.2 录音期间进设置页再返回，主窗口回到「正在录音」界面而非「开始录音」。
- R7.3 录音在主窗口之外被停止（例如关窗拦截路径）时，主窗口的录音 UI 应自行收敛到空闲态，不停留在过期的「正在录音」。

### R8 关窗拦截
- R8.1 录音进行中关闭主窗口时不直接关闭，改为呈现三个选择：停止并保存录音、继续录音（返回应用）、取消关闭。
- R8.2 「停止并保存录音」执行 `record_stop` 完成落盘，向用户展示保存路径，然后退出应用。此路径**不**自动建会议行、**不**自动启动转写；提示文案须告知用户下次可用「导入音频并转写」处理该文件。
- R8.3 非录音状态下关闭主窗口的行为与现状一致，不增加任何询问。
- R8.4 关闭主窗口后应用进程必须退出（悬浮窗作为常驻第二窗口不得阻止退出）。

### R9 无障碍与动效
- R9.1 呼吸红点与电平条在 `prefers-reduced-motion: reduce` 下降级为静态，与现有波形图的处理一致（`RecordingWaveform.tsx:24-32`）。
- R9.2 计时区域对屏幕阅读器可读。

## Out of scope

- 静音检测 / VAD / 自动停止录音。
- 悬浮窗内的停止按钮（与之绑定的录音会话所有权重构）。
- 系统通知、全局快捷键；空闲时的常驻托盘（托盘仅录音期间可见）。
- 日历集成、会议软件进程检测、WASAPI audio session 枚举。
- 主窗口标题栏显示计时、任务栏角标。
- 孤儿 `.wav.partial` 启动扫描与恢复。
- 暂停 / 恢复录音（既有 out of scope，见 `archive/2026-07/07-25-meeting-recording/prd.md:50-51`）。
- 尾部静音裁剪、转写前静音跳过。
- macOS / Linux 支持（录音本身仅支持 Windows）。

## Acceptance criteria

| # | 场景 | 可观测结果 |
|---|---|---|
| A1 | 点击「开始录音」 | 悬浮窗出现；主窗口离开任务栏；系统托盘出现 Meetly 图标；计时从 00:00 递增 |
| A2 | 在主窗口点「停止并转写」 | 悬浮窗与托盘消失；主窗口回到前台并进入转写流程 |
| A3 | 录音中（主窗口已从托盘打开后）最小化主窗口，并把其他应用最大化置于前台 | 悬浮窗仍然可见且计时持续 |
| A4 | 录音中在 Alt+Tab 与任务栏中查找悬浮窗 | 两处都不出现悬浮窗 |
| A5 | 录音中点击悬浮窗折叠 | 只剩呼吸红点，窗口收紧；再次点击恢复药丸并显示正确时长 |
| A6 | 录音中拖动悬浮窗到新位置，停录后重启应用再录音 | 悬浮窗出现在上次拖到的位置 |
| A7 | 保存位置指向已断开的外接显示器 | 悬浮窗出现在主显示器默认位置，不消失 |
| A8 | 录音持续超过 1 小时 | 计时显示为 `1:00:0X` 形式，布局不抖动 |
| A9 | 录音中从托盘打开主窗口后点齿轮进设置，再返回 | 主窗口显示「正在录音」，计时与悬浮窗一致（不归零） |
| A10 | 录音中点击悬浮窗「打开 Meetly」或托盘图标（主窗口已隐藏） | 主窗口显示并聚焦，且停在录音界面；托盘仍在 |
| A11 | 录音中关闭主窗口 | 出现三选一询问，窗口未关闭 |
| A12 | 在 A11 中选「停止并保存录音」 | 提示保存路径；托盘消失；该路径存在完整音频文件；应用退出，进程结束 |
| A13 | 在 A11 中选「继续录音」 | 主窗口保留，录音未中断，悬浮窗计时连续 |
| A14 | 非录音状态关闭主窗口 | 无询问，直接关闭，进程结束；无托盘残留 |
| A15 | 开启系统「减少动态效果」后录音 | 红点与电平条静态呈现，无呼吸/抖动动画 |
| A16 | 录音中托盘右键「退出」 | 主窗口出现并弹出与关窗相同的三选一询问 |

## Risks

| 风险 | 影响 | 处置 |
|---|---|---|
| 屏幕共享时悬浮窗对会议全员可见 | 隐私/尴尬 | 折叠态缓解；不提供录音期间彻底隐藏（用户已决策） |
| 独占全屏应用可能盖住置顶窗口 | 最需要提醒的时刻恰好不可见 | **待手工验证**：腾讯会议 / Zoom 全屏态下置顶是否有效；确认后把结论写回本行。无法覆盖时定性为本方案固有限制，不在本任务引入托盘等备用通道 |
| 透明无装饰窗口在 Win11 出现 1px 白边 | 视觉瑕疵 | `shadow` 设为 false，圆角与阴影用 CSS 实现（见 `research/tauri-floating-window.md`） |
| 常驻第二窗口阻止应用退出 | 关窗后进程残留 | R8.4 显式退出，并列入验收 A12 / A14 |
| 两个窗口同时轮询 `record_status` | 无谓的 IPC 开销 | 悬浮窗折叠态降频轮询；主窗口只做低频状态同步，电平仍由现有波形图负责 |
